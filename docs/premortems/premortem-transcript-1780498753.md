# Premortem Transcript — the EXTRACTION/PORT (dstack-auth-extraction)

**Run:** 2026-06-03 (ts 1780498753)
**Target:** the drafted spec `docs/specs/dstack-auth-extraction.md` (port dstackgres's auth code), assumed implemented-and-failed.
**Method:** 6 parallel investigators, each grounded in the spec + the AttestMesh code + the dstackgres source (`/tmp/dstackgres`).

> Third fix attempt, third strong negative — but this one **converges the whole thread onto a small, safe step.** The wholesale port fails concretely (12× scope, two incompatible diamonds, the CSK *is* the Postgres envelope, an alloy 0.8-vs-1 wall, two mesh/liveness systems, and a mock that hides wrong preimages). The answer that survives across **all three** fix premortems: keep v1's working scaffolding and surgically extract **only the verification primitive** — don't port the 35k-line system, and don't reinvent.

## Context

- **What:** port dstackgres's proven auth code (`contracts/teesql-group-auth`, `crates/sqlx-ra-tls`, `crates/teesql-data-sidecar`, gas-payment) into AttestMesh, rebranded, dropping Postgres/control-plane/leader-lease, folding the verifier into the attestor facet.
- **Who:** the team doing the port; everyone downstream of a working, correct dstack integration.
- **Success:** a clean, finished port that passes against a real dstack proof and brings up a mesh.

## Raw failure modes
E1 the extraction boundary isn't clean · E2 two incompatible diamonds collide · E3 the rebrand silently breaks the security-critical verification · E4 "proven" hides version skew + latent TODOs + a frozen upstream · E5 kept AttestMesh glue doesn't fit the ported mesh · E6 "extraction" undersells a re-architecture that stalls half-done.

## Synthesis

**Most likely / most immediate — E6 + E2 (the wholesale port can't even build).** dstackgres's data-sidecar is **35,323 lines / 46 modules — 12× v1's 2,777-line sidecar**; the contract subset is 3,885 lines vs v1's 1,556. The two diamonds are mutually exclusive: AttestMesh's `MemberStorage` (`attestmesh.storage.Member`, rich record, `memberId = keccak256(abi.encode(cluster,member,attestorId))`, an EIP-4337 `IAccount` `ClusterMember`) vs dstackgres's (`teesql.storage.Member` = just `address cluster`, membership in `CoreStorage`, `memberId = keccak256(derivedPubkey)`, a UUPS-forwarder `DstackMember` with no 4337). `Namespaces.t.sol`'s pinned slot assertions detonate the instant a rebranded `teesql.storage.Member` lands beside `attestmesh.storage.Member`; the two memberId formulas orphan every "surviving" `MessageFacet`/CSK lookup. First `cargo build` fails on alloy 0.8-vs-1 and missing `teesql-common` workspace crates. Six weeks in: a chimera that doesn't run, with v1's once-green tests now red.

**Most dangerous — E3 (the rebrand silently breaks, or weakens, verification).** v1's current `DstackFacet` already recovers over the *wrong* preimage (`keccak256(abi.encode("dstack.app", appKey, composeHash))`) vs dstack's real `keccak256(abi.encodePacked("dstack-kms-issued:", bytes20(codeId), appCompressedPubkey))`, and `MockKmsChain` was built to match the wrong facet — a **closed loop where any preimage round-trips**. A port that fixes the facet but not the mock (or rebrands `"dstack.app"`→`"attestmesh.app"` and leaves it) passes CI and rejects every real proof; a `Proof` struct field-reorder during the port silently maps bytes into `kmsSignature`/`appCompressedPubkey` and can recover *attacker-chosen* addresses while the mock still passes. The literal `"dstack-kms-issued:"` has **zero** test coverage.

**The hidden assumption.** That dstackgres's auth is a *separable, finished module* you copy-and-rebrand — when it is a tightly-coupled subset of a system several times AttestMesh's size, fused to Postgres (the CSK `ClusterSecrets` struct's wire fields are `pg_replication_password`/`backup_encryption_key_hex`/`control_plane_key_hex`; `cold_start_election` takes `&PgManager` and reads WAL LSNs), built on a different diamond, a different memberId algebra, a different member-contract ABI, a different mesh/IP scheme (`10.42.0.0/24` octet table vs v1's `10.13.0.0/16` keccak), and a different toolchain (alloy 1).

**The convergent recommendation (across all three fix premortems): surgical extraction, not wholesale port, not reinvention.**
1. **Port ONLY the verification primitive** — `DstackSigChain` (the real `"dstack-kms-issued:"` preimages + `recover`/`compressedToAddress`) — the ~200-line crown jewel v1 got wrong and dstackgres got right. It is self-contained (no Postgres/diamond/mesh entanglement). Replace v1's invented `DstackSigChain` + the `dstack_register` preimages with it.
2. **Fix the mock + add a real fixture.** Rewrite `MockKmsChain` to produce *real-format* proofs and check in a captured real dstack proof; add a test that references the literal `"dstack-kms-issued:"`. Kills E3's closed loop.
3. **Fix F2 in v1's own `bundler.rs`** (sponsor-then-sign), using dstackgres's `gas_payment/alchemy.rs` as a **read-only reference** — do *not* port it across the alloy 0.8→1 boundary (avoids E4's compile wall).
4. **Fix v1's remaining gaps AttestMesh-native** (CSK persistence → the LUKS data disk; originator selection; the encrypted-endpoint rendezvous over `MessageFacet`), *informed by* dstackgres's patterns but not by importing the 35k-line entangled modules (avoids E1/E5/E6).
5. **Do NOT graft two diamonds or port the data-sidecar wholesale** (avoids E2/E6's chimera). Keep v1's diamond/`MessageFacet`/heartbeat/mesh-IP — they pass tests.
6. The deeper "is v1's whole architecture right" question is separate; v1 works today — refine incrementally, never big-bang-replace.

### Pre-work checklist

- ☐ No `teesql.storage.*` namespace, no second `memberId` formula, no second `ClusterMember`/`DstackMember`, no second CIDR, ever land in the tree (E2/E5).

## Agent deep-dives (verbatim)

### E1 — The extraction boundary isn't clean
**Story.** "Drop the Postgres parts" was drawn through structs, not modules. The CSK the spec ports wholesale — `ClusterSecrets` (`cluster_secrets.rs`) — *is* the Postgres envelope: its wire fields are `pg_replication_password`, `backup_encryption_key_hex`, `control_plane_key_hex`, `control_plane_log_key_hex`. `group_auth.rs` `pub use`s `ClusterSecrets`; `onboarding.rs` imports it from `group_auth`. Keep the four Postgres/control-plane fields you swore to drop, or delete them and break the shared wire format, every `is_complete()`, the writer's co-located files, and the `claimLeader(ciphertext)` onboarding payload. `cold_start_election.rs` (the "originator/genesis" fix) *is* the leader-lease machinery: it takes `pg: &PgManager`, reads `pg_last_wal_replay_lsn()`, calls `leader_lease()`/`claim_leader_with_gather()`. Sever the WAL/lease calls and there is no election left. On-chain, `CoreFacet.register()` writes a `Member` with `dnsLabel`; `onboard()` shares `CoreStorage` with `claimLeader`/`leaderLease`/`updateEndpoint`.
**Assumption.** That "auth/CSK/election" and "Postgres/leader/control-plane" are separable subsystems, when they are the same code through shared structs + a shared leader-lease loop.
**Warnings.** The first port (copying `cluster_secrets.rs`) forces a yes/no on `pg_replication_password` in the CSK wire format — no neutral answer. A `cargo build` of the "subset" immediately demands `crate::postgres::PgManager`, `wal_bearer_writer`, `boot_restore`.

### E2 — Two incompatible diamonds collide
**Story.** Both extend `SolidStateDiamond`, so "keep base, replace core" looked safe — but the facet sets were authored against disjoint ERC-7201 regimes. AttestMesh's `MemberStorage.Layout` (`attestmesh.storage.Member`, slot `0xb467…1200`) packs the full record; dstackgres's (`teesql.storage.Member`, slot `0x4880…0500`) is a single `address cluster`, with membership in `CoreStorage` (`instanceToMember`/`derivedToMember`/`leaderEpoch`/`dnsLabel`). Rebranding recomputes every slot; you either collide the two `…Member` namespaces or keep both and read membership from two slots that never sync — `Namespaces.t.sol` detonates. memberId is the second irreconcilable axis (`keccak256(abi.encode(this,member,attestorId))` vs `keccak256(derivedPubkey)`) — `MessageFacet`/CSK/heartbeat/mesh-IP are keyed to the triple-hash id; importing `CoreFacet` re-keys every member. And `ClusterMember` is an EIP-4337 `IAccount` smart wallet while `DstackMember` is a UUPS forwarder with no 4337 surface — the bundler/webhook and boot-gate assume opposite sender semantics.
**Assumption.** A shared `SolidStateDiamond` base means two diamonds compose — but a diamond's real interface is its storage map + memberId algebra + member ABI, and on all three these forks are mutually exclusive.
**Warnings.** `Namespaces.t.sol`'s pinned slot assertions fail the build the instant a rebranded `teesql.storage.Member` lands. Two live memberId formulas with no migration mapping: a ported member looked up by surviving `MessageFacet`/CSK returns the zero record.

### E3 — The rebrand silently breaks (or weakens) verification
**Story.** The port "succeeded" — `forge test` green, rebrand clean — but the first real dstack CVM is rejected `KmsAppKeySigInvalid`, because the tests assert against a mock that signs the *invented* preimages. dstackgres recovers over `keccak256(abi.encodePacked("dstack-kms-issued:", bytes20(codeId), appCompressedPubkey))`; v1's facet recovers over `keccak256(abi.encode("dstack.app", appKey, composeHash))` — different domain, fields, and `abi.encode` (padded) vs `abi.encodePacked`. The app→derived step diverges identically (`"dstack.instance"`+`abi.encode` vs `purpose+":"+hex`). `MockKmsChain.buildProof` was written to match the *wrong* facet, so it's a closed loop — any preimage round-trips. A reordered `Proof` struct silently maps bytes into `kmsSignature`/`appCompressedPubkey`, recovering attacker-chosen addresses while the mock passes. The literals `"dstack-kms-issued:"`, the `":"` joiner, and `bytes20(codeId)` packing have zero coverage.
**Assumption.** A green suite proves the verifier correct, when it only proves it agrees with a mock built to mirror the wrong code it replaces.
**Warnings.** The "port `DstackSigChain`" PR changes the facet but leaves `MockKmsChain.sol`/`ClusterBringup.t.sol` untouched (or only rebrands strings); no test references `"dstack-kms-issued:"`; `grep` still finds `abi.encode(` or `"dstack.app"`/`"attestmesh.app"` in the post-port verifier.

### E4 — "Proven" hides version skew + latent TODOs + a frozen upstream
**Story.** AttestMesh pins alloy **0.8**; dstackgres pins alloy **1** — a major break in the signer/`Signature`/provider APIs. The two ported crown jewels (`gas_payment/{alchemy,userop}.rs`, `dstack.rs`) are written against alloy 1, so the port won't compile, or the LightAccount-v2 byte + `userOpHash` preimage shift silently and every UserOp reverts — reopening F2. Bumping AttestMesh to alloy 1 cascades into `thiserror`/contract changes. The ported `DstackKmsAdapterFacet`/`CoreFacet` carry `TODO: consider gating to require caller via createMember dispatch` + `TODO(future-kms-dispatch)` hardcoding the single KMS adapter — benign in dstackgres (sole caller), but in AttestMesh's *pluggable-attestor* diamond the un-gated verify surface is directly callable and the hardcoded dispatch contradicts the "attestation-method-agnostic core" directive. And TeeSQL's product is on hold (master §13) — a frozen upstream with no fixes coming.
**Assumption.** "Proven in dstackgres" was read as "correct and complete in isolation," when it meant "correct given dstackgres's pinned versions, its KMS/monitoring context, and its tolerated TODOs."
**Warnings.** First `cargo build` of the ported `gas_payment`/`dstack.rs` fails on alloy 0.8-vs-1 trait mismatches (or compiles but the Sepolia UserOp reverts). `grep "TODO(future-kms-dispatch)\|consider gating"` over the ported `contracts/src` returns dstackgres markers verbatim.

### E5 — Kept AttestMesh glue doesn't fit the ported mesh
**Story.** Two endpoint-exchange protocols write the same `PeerInfo` from incompatible sources: AttestMesh learns a peer via sealed-box `PeerEndpoint{host,port,wg_pub,ed25519_pub}` over `MessageFacet`; the ported dstackgres path learns the WG IP via `endpoint_crypto` (AES-GCM over a cluster key on the `10.42.0.0/24` literal) and the pubkey via `wg_relay`→`setMemberWgPubkeyAttested` (recovered from quote `report_data[0..32]`). A peer's WG pubkey now has two publishers — `NetworkFacet.publishWgKey` (self-asserted) and `WgMeshFacet` (quote-derived, `WgPubkeyAlreadyClaimed`-gated) — that disagree, so the handshake never completes. Mesh-IP collides head-on: `10.13.x.x/16` from `keccak256(memberId)` vs `10.42.0.0/24` from the contract's octet table — two non-equal IPs per peer, heartbeats land nowhere. Liveness double-governs: AttestMesh gates `healthy` on `first_converged`; dstackgres has `pairing_check`/`fence_watchdog`/`degraded_mode` assuming a leader/primary model AttestMesh dropped — the ported watchdog arms on `self_is_leader true→false`, a flag never set, so it's inert while convergence never latches.
**Assumption.** That endpoint exchange, wg-pubkey publication, and liveness are mix-and-match modules — rather than one coupled contract where the IP scheme, pubkey source, and health gate must agree on the same peer identity/topology.
**Warnings.** Two subnets live simultaneously (`cidr.rs` `10.13.0.0/16` vs `endpoint_crypto`/`WgMeshFacet` `10.42.0.0/24`). Two wg-pubkey writers compile side by side and `PeerEndpoint.wg_pub` matches neither's on-chain value.

### E6 — "Extraction" undersells a re-architecture that stalls
**Story.** Six weeks in, the repo is a chimera. The data-sidecar is 35,323 lines / 46 modules — 12× v1's 2,777; the contract subset 3,885 vs 1,556. "Drop the Postgres parts" became surgery on every file: `group_auth.rs` has 170 pg/control-plane refs, `onboarding.rs` 216, `cold_start_election.rs` 89. The sidecar won't build (missing `teesql-common` + four workspace crates); the diamonds never reconciled; alloy 0.8-vs-1 unhandled; two mesh/liveness models sit side by side, neither wired. Some facets rebranded, the sig-chain lib swapped, but nothing runs and v1's once-green tests are red. The sunk cost makes abandonment feel wasteful, so it limps. (Note: some dstackgres paths under `open-source/*` are uninitialized submodule mirrors; the real code is under `contracts/`/`crates/` — but the mixed layout itself complicates "what to port.")
**Assumption.** That dstackgres's auth is a separable, finished module you copy and rename — when it's a tightly-coupled subset of a system several times AttestMesh's size, fused to Postgres, a different diamond, and a different toolchain.
**Warnings.** First `cargo build` after copying any sidecar module fails on missing workspace crates + the alloy mismatch — the moment "find-replace" needs dependency re-architecture, "port" has become "rewrite." The repo accumulates half-rebranded `teesql_*` symbols alongside `attestmesh_*` ones.
