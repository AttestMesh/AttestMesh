Premortem — the v2 design (dstack-attested-quorum-membership)

We built it as specced. Frame: months from now, it failed — the quorum was subverted, the verification broke, or the coordination didn't scale.

Second strong negative result. v2 dissolves the rejected rework's P1/P2, but introduces a fatal Sybil hole (V1), rests on a dstack verifier that isn't a reusable library (V2), and suffers correlated TCB mass-eviction (V4), a bootstrap chicken-and-egg (V3), F2 coupling that makes votes un-landable (V5), and the same "why on chain" erosion (V6).
Meta-finding (across both fix premortems): we keep trying to make the chain do trustless attestation, and every approach either can't, is insecure, or guts the thesis. The real, unmade decision is chain-as-VERIFIER vs chain-as-COORDINATOR — make it explicitly, instead of iterating governance mechanics.
What
On-chain attestation policy + off-chain mutual DCAP verification + a >50% multisig of members for admission/eviction. Attestation = per-instance TDX quote (report_data binds pubkeys). Self-asserted voting key. Owner = policy + genesis + break-glass.
Who
The team building it; operators/nodes who need only attested, approved-software, independent nodes to govern.
Success
The quorum admits only genuine independent attested nodes; verification is reliable; the chain has a defensible reason to exist.
Method
6 parallel investigators grounded in the spec + the real dstack source (verifier/, ra-tls/, dcap-qvl, kms/, guest-agent, attestation.md) + the AttestMesh code. 2026-06-03.

Synthesis — read this first

Most likely / most immediate

V5 — nothing works until F2 is fixed, then admission is an O(N) stall.

Votes are EIP-4337 UserOps through bundler.rs::submit, which (lines 63-69) signs the userOpHash before Alchemy inserts paymasterAndData → every op rejected (premortem F2) → no vote lands → member #2 is never admitted. Even fixed, a majority of the full set must each verify off-chain and land a vote tx per join; slow eviction keeps memberCount inflated, raising the threshold — worse as the cluster grows.

Most dangerous

V1 — no Sybil resistance. A >50% multisig of attested nodes is not a multisig of distinct parties.

Attestation proves "runs approved software," not "is an independent party." One operator runs a majority of CVMs that legitimately pass every peer's DCAP check, holds all their self-asserted voting keys, and votes them as a bloc — owning admission and eviction. It admits non-attested confederates (its majority just votes yes; the contract verifies nothing) and evicts the honest minority. The data-plane DCAP gate doesn't help (takeover nodes run the good image); the vote-audit hash is forensics, not prevention. The original design avoided this because the owner curated membership — the move to a peer quorum introduced the Sybil surface while removing the chain's verification role.

The hidden assumption

That "attested" = "independent" — and that holding attestation state on chain is itself the value.

Democratizing admission to a quorum of attested nodes assumes they're distinct honest parties, which attestation never establishes (V1). And the "reuse dstack's verifier" plan assumed a reusable offline library (V2) — but dstack's verifier downloads the OS image and recomputes measurements with dstack-mr and is an HTTP service, not a verify(quote)→bool lib.

The fork to decide

Chain-as-VERIFIER vs chain-as-COORDINATOR.

  • VERIFIER (trustless): the only design where the chain enforces something no single party is trusted for is on-chain DCAP quote verification (the deferred path) — heavy (gas, PCS/cert mgmt, dcap-qvl-on-EVM), milestone-scale, but it's the defensible on-chain product.
  • COORDINATOR (pragmatic): verification is off-chain; the chain is policy + registry + encrypted messaging + governance. Then answer "why on chain" honestly (neutral shared state, censorship-resistance, multi-tenant Indexer) and fix Sybil with owner-curated admission, not a peer quorum.

The revised plan

  1. Don't build v2 as specced. Sound on P1/P2, unsound on Sybil (V1), over-claims reusable verification (V2).
  2. For the realistic use case — owner-deployed cluster infrastructure — owner-curated admission is correct and Sybil-sound. The owner deploys the nodes, so the owner authorizes membership (the original allowlist + factory model); attestation ensures approved software. The >50% quorum solved decentralized admission — a problem an owner-operated cluster doesn't have. Keep mutual off-chain attestation for the data plane.
  3. Make the verifier-vs-coordinator fork explicit and written down with the "why on chain" answer (V6).
  4. Implementation facts under any model: dstack's verifier is not a drop-in lib (vendor dcap-qvl + dstack-mr, own the TCB-acceptance policy — validate_tcb doesn't gate on tcb_status); fix F2 first; design a pre-membership rendezvous transport (RA-TLS is cert-only, peer_grpc is wireguard-only); handle correlated TCB recovery (tolerate SwHardeningNeeded + a grace, not instant mass-eviction).

The six failure modes

V1 · No Sybil resistance (attested ≠ independent)

Certain
One operator runs a majority of CVMs on the approved image — all pass every peer's DCAP check — holds all their self-asserted voting keys, and votes the bloc. Past floor(N/2)+1 she owns admission + eviction: admits non-attested confederates, evicts the honest minority. Data-plane DCAP doesn't help (her nodes run the good image); the audit hash is forensics. A multisig of attested nodes ≠ a multisig of distinct parties.
Underlying assumption
Attestation of approved software was conflated with proof of independent operatorship.
Early warning signs
Growth dominated by nodes sharing FMSPC/ASN/PCCS fingerprints with no distinctness check in proposeMember/voteAdmit; correlated ownerKeys while distinct operating entities stay flat.

V2 · dstack's verifier isn't a reusable library

Certain
CvmVerifier::verify() (verifier/src/verification.rs:400) doesn't check measurements against an allowlist — it downloads the OS image and recomputes MRTD/RTMR with dstack-mr, in a Rocket HTTP binary. The reusable surface is dcap-qvl/dstack-attest; you hand-build the policy layer. Needs live PCCS collateral (FMSPC-keyed) — no collateral, no verified peer, no mesh/vote. And validate_tcb doesn't gate on tcb_status — your TCB policy is unverified (too lax admits bad, too strict rejects good).
Underlying assumption
dstack ships peer-quote verification as a reusable, offline library.
Early warning signs
"Reuse the verifier" becomes vendoring dcap-qvl+dstack-mr+PCCS plumbing; real-TDX tests fail with "Failed to get collateral" or MRTD/RTMR mismatch after an image/TCB update.

V3 · Bootstrap chicken-and-egg + unverified genesis

High
A newcomer must let a majority DCAP-verify it over "RA-TLS" — but dstack's ra-tls is cert-format only (no listener); the only member transport is peer_grpc (wireguard-only, gated on being verified) and PeerEndpoint over member-only MessageFacet. So a non-member has no channel to be verified → admissions dry up. And member #1 enters by owner fiat with zero peer verification; at N=1 it's the whole majority and can admit accomplices before any honest peer checks it.
Underlying assumption
"Verify each other over RA-TLS" is a usable bootstrap primitive; owner-fiat genesis is a safe stand-in for verification.
Early warning signs
No transport is named for the attestation exchange; a fresh proposeMember accrues zero votes; no test ever DCAP-verifies the genesis node.

V4 · Correlated TCB-recovery mass-eviction

High
Intel publishes a TDX recovery; within one PCCS refresh every node's dcap-qvl flips UpToDate→OutOfDate (status is Intel-controlled, identical for the homogeneous fleet). The policy accepts only UpToDate, so every member fails every peer at re-attestation and files voteEvict on everyone; memberCount collapses below quorum in one block-span → wedge (break-glass can't re-admit). Separately, near 50% eviction oscillates on transient slowness/reboots.
Underlying assumption
Re-attestation failure is independent and node-local, so symmetric >50% eviction safely removes one bad node.
Early warning signs
voteEvict spike all citing the same fresh advisory/tcb_status transition; memberCount saw-tooth churn with reason "unreachable/timed-out re-attest."

V5 · O(N) admission + coupling to the broken F2 transport

Certain
Every join needs a majority of the full set to each verify + land a voteAdmit UserOp; clusters churn, so wall-clock is dominated by overlapping ceremonies blocked on the slowest member, and inflated memberCount raises the threshold. And none land: votes are UserOps through bundler.rs::submit, which signs before paymasterAndData is inserted (F2) → AA24 reject on every op → no quorum ever forms. One bundler + webhook is a censorable chokepoint for the whole control plane.
Underlying assumption
Per-event all-member majority voting is cheap and reliable, and the gasless UserOp transport works.
Early warning signs
A 3–5-node rehearsal where proposeMember never reaches quorum (offline node or AA24 on voteAdmit); pending-admission latency climbs with size; memberCount drifts above live count.

V6 · Strategic — the chain verifies nothing → "Safe + a message board"

Strategic
§1's "attestation chain the cluster contract verifies" and the Join invariant die; §4.1's attestor-facet checks evaporate. What remains is a registry + relay + key bulletin + a vote tally — each a thing a Safe or coordinator already does. The chain can't see whether a voter ran DCAP (quoteHash is self-asserted in the vote), can't tell honest from colluding signers, can't enforce independence — it only orders votes and stores ciphertext. Fix #1 collapsed into DstackApp; fix #2 collapses into "Safe + bulletin board."
Underlying assumption
A public chain adds value by holding attestation-derived state, when its only defensible value is independently verifying what no single party is trusted for.
Early warning signs
"Why not a Safe + a coordinator service?" is answered operationally, not "the chain verifies attestation no operator is trusted to"; the Indexer/paymaster stack's only consumers already share a DCAP'd mesh and could swap the bytes peer-to-peer.
