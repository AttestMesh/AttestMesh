# Premortem Transcript — the v2 design (dstack-attested-quorum-membership)

**Run:** 2026-06-03 (ts 1780495534)
**Target:** the drafted spec `docs/specs/dstack-attested-quorum-membership.md`, assumed implemented-and-failed.
**Method:** 6 parallel investigators, each grounded in the spec + the real dstack source (`/tmp/dstack-real`) + the AttestMesh code.

> Second strong negative result. v2 **dissolves the rework's P1/P2** (the compose hash is read from a verified quote, not self-asserted; no per-`app_id` KMS dependency) — but introduces a **fatal Sybil hole**, rests on a dstack verifier that **isn't a reusable library**, and suffers **correlated TCB mass-eviction**, a **bootstrap chicken-and-egg**, and the same **"why on chain" erosion**. Together with the prior premortem it exposes the project's real fork: **is the chain a verifier or a coordinator?**

---

## Context

- **What:** on-chain attestation POLICY + off-chain mutual DCAP verification (every member verifies every peer's TDX quote against the on-chain policy) + a `>50%` multisig of members for admission/eviction. Attestation = per-instance TDX quote, `report_data = keccak256(xPub‖wgPub)`, via dstack `GetQuote`. Self-asserted voting key. Owner = policy + genesis-admit + break-glass.
- **Who:** the team building it; operators/nodes who need membership to be sound (only attested, approved-software, *independent* nodes govern).
- **Success:** the quorum admits only genuine independent attested nodes; verification is reliable; the mesh forms; the chain has a defensible reason to exist.

## Raw failure modes
V1 no Sybil resistance (attested ≠ independent) · V2 off-chain DCAP verifier isn't reusable + needs live collateral + an unverified TCB policy · V3 bootstrap chicken-and-egg + unverified genesis · V4 correlated TCB-recovery mass-eviction + griefing oscillation · V5 O(N) admission + coupling to the still-broken F2 transport · V6 strategic: the chain verifies nothing → "Safe + a message board."

---

## Synthesis

**Most likely / most immediate failure — V5.** Nothing works at all until F2 is fixed: votes are EIP-4337 UserOps through `bundler.rs::submit`, which (confirmed, lines 63-69) signs the userOpHash before Alchemy inserts `paymasterAndData`, so every sponsored op is rejected — no vote can land, no quorum can form, member #2 is never admitted. Even after F2, admission is an O(N) ceremony (a majority of the *full* set must each verify off-chain and land a vote tx), stalling on any slow/offline member, with slow eviction keeping `memberCount` inflated and thus *raising* the threshold — worse as the cluster grows.

**Most dangerous failure — V1 (no Sybil resistance).** Attestation proves "runs approved software," not "is an independent party." One operator runs a *majority* of CVMs that legitimately pass every peer's DCAP check (they run the approved image), holds all their self-asserted voting keys, and votes them as a bloc — owning admission and eviction. It admits non-attested confederates (its majority just votes yes; the contract verifies nothing) and evicts the honest minority. The data-plane DCAP gate doesn't help (the takeover nodes run the *good* image); the vote-audit hash is forensics, not prevention. **A `>50%` multisig of attested nodes is not a `>50%` multisig of distinct parties** — and nothing in the design enforces independence.

**The hidden assumption.** Three, with one root: that **attested = independent** (V1), that **the chain holding attestation-derived state is itself valuable** (V6), and that **dstack ships a reusable peer-quote verifier** (V2). The deepest: democratizing admission to a quorum of attested nodes assumes those nodes are distinct honest parties — which attestation never establishes. The *original* design didn't have this hole because the **owner curated membership** (the allowlist + the factory); the move to a peer quorum *introduced* the Sybil surface while *removing* the chain's verification role.

**The meta-finding (across both fix premortems).** We keep trying to make the chain do trustless attestation, and every approach either can't (dstack has no cheap on-chain verification), is insecure (self-asserted fields, Sybil), or guts the thesis. **The real, unmade decision is: chain-as-VERIFIER vs chain-as-COORDINATOR.** Make it explicitly instead of iterating governance mechanics.

### The revised plan
1. **Do not build v2 as specced.** It is sound on P1/P2 but unsound on Sybil (V1) and over-claims reusable verification (V2).
2. **Make the fork explicit:**
   - **Chain-as-VERIFIER (trustless):** the only thing that's both trustless *and* a defensible on-chain product is **on-chain DCAP quote verification** (the deferred path). Heavy (gas, PCS/cert management, `dcap-qvl`-on-EVM), milestone-scale — but it's the one design where the chain enforces something no single party is trusted for. Decide if that's the product.
   - **Chain-as-COORDINATOR (pragmatic):** accept that verification is off-chain; the chain is policy + registry + encrypted messaging + (optionally) governance. Then **answer "why on chain" honestly** (neutral shared state, censorship-resistance, multi-tenant Indexer) — and **fix Sybil by owner-curated admission, not a peer quorum.**
3. **For the realistic use case (owner-deployed cluster infrastructure), owner-curated admission is correct and Sybil-sound.** The owner deploys the nodes, so the owner authorizes membership (the original allowlist + factory model); attestation (verified by the owner/KMS, or by peers off-chain as defense-in-depth) ensures approved software. The `>50%` quorum was solving *decentralized admission* — a problem an owner-operated cluster doesn't have. Bring back owner authority for admission; keep mutual off-chain attestation for the data plane.
4. **Implementation facts that hold under any model (from the agents):**
   - dstack's `verifier` is **not** a drop-in library — it downloads the OS image and recomputes MRTD/RTMR with `dstack-mr` and is an HTTP service. You will vendor **`dcap-qvl` + `dstack-mr`** and own the **TCB-acceptance policy** yourself (`validate_tcb` deliberately does not gate on `tcb_status`). Budget for it.
   - **Fix F2 first** — no governance/registration tx lands until the paymaster sign-ordering is fixed.
   - **Design a pre-membership rendezvous transport** — RA-TLS in dstack is cert-format-only (no listener); `peer_grpc` is wireguard-only and `PeerEndpoint` is member-only, so a newcomer currently has no channel to be verified.
   - **Handle correlated TCB recovery** — `tcb_status` is a global Intel-controlled input that flips for the whole homogeneous fleet at once; an instant `>50%` mass-eviction wedges the cluster. Use a policy that tolerates `SwHardeningNeeded`/advisories with a re-attestation grace, not instant eviction.

### Pre-implementation checklist
- ☐ The verifier-vs-coordinator decision is made and written down, with the "why on chain" answer (V6).
- ☐ If coordinator: admission is owner-curated (Sybil-sound), not a peer quorum (V1).
- ☐ A real dstack CVM + `dcap-qvl` + a PCCS verifies one real peer quote off-chain, end-to-end, with an explicit TCB-acceptance policy (V2).
- ☐ F2 (paymaster sign-ordering) is fixed and one sponsored tx lands on Sepolia (V5).
- ☐ A pre-membership rendezvous channel exists for the attestation handshake (V3).
- ☐ A TCB-recovery rehearsal does not mass-evict the fleet (V4).

## Agent deep-dives (verbatim)

### V1 — No Sybil resistance (attested ≠ independent)
**Story.** Mallory doesn't break attestation — she satisfies it. She runs CVMs on the exact approved image; each calls `GetQuote(report_data=keccak256(xPub‖wgPub))`, producing quotes every honest member's DCAP verifier accepts (real Intel chain, allowlisted measurements, correct binding). Each is admitted by legitimate `voteAdmit` calls from diligent peers — nothing asks "is this the same operator as the last twelve?" Because the voting key is self-asserted, Mallory holds every node's key and votes the bloc herself. Past `floor(N/2)+1` of `memberCount` she controls the multisig: `voteAdmit` now admits non-attested confederates (her majority votes yes; the contract verifies nothing), `voteEvict`/`prune` removes the honest minority. The data-plane DCAP gate doesn't save the control plane — her takeover nodes run the *good* image and pass it; the vote-audit hash is forensics, not prevention.
**Assumption.** Attestation of approved software was conflated with proof of independent operatorship.
**Warnings.** Membership growth dominated by nodes sharing infra fingerprints (same FMSPC/PPID platform, ASN/IP block, PCCS) with no operator-distinctness check anywhere in `proposeMember`/`voteAdmit`; bursts of pending registrations + correlated `ownerKey`s while the count of *distinct* operating entities stays flat.

### V2 — Off-chain DCAP verifier isn't reusable; live collateral; unverified TCB policy
**Story.** "Reuse dstack's verifier" is largely false. `dstack-verifier`'s `CvmVerifier::verify()` (`verifier/src/verification.rs:400`) doesn't check quote measurements against an allowlist — after DCAP it **downloads the OS image tarball over HTTP** (`download_image`, ~line 640) and **recomputes MRTD + RTMR0-2 with `dstack-mr`** (QEMU/OVMF/kernel emulation) and asserts equality. It's a Rocket HTTP binary, not a `verify(peer_quote)→bool` lib; the reusable surface is `dcap-qvl`/`dstack-attest`, and the team must hand-build the measurement-policy layer. Operationally, the real path is `dcap_qvl::collateral::get_collateral_and_verify(quote, PCCS_URL)` (`dstack-attest/src/attestation.rs:807`) — every node must reach a live PCCS/Intel PCS for FMSPC-keyed PCK/TCB/QE-identity; locked-down egress or a flaky PCCS → "Failed to get collateral" → no verified peer → no tunnel/CSK/vote, and a majority outage freezes governance. Finally, `validate_tcb` (~line 1160) checks only the debug bit + mrSignerSeam and deliberately does **not** decide on `tcb_status` — so each node's hand-rolled TCB-acceptance policy is unverified: too lax admits a down-rev'd peer, too strict rejects honest ones, and the chain catches neither.
**Assumption.** That dstack ships peer-quote verification as a reusable, self-contained, offline library — when it ships an HTTP service that re-derives measurements from a downloaded image and needs live Intel collateral + a caller-supplied TCB policy.
**Warnings.** "Reuse the verifier" becomes vendoring `dcap-qvl` + `dstack-mr` + image-download/PCCS plumbing (LOC/deps balloon; the sidecar still ships a *mock* quote in `dstack.rs`); first real-TDX multi-node test intermittently fails to admit/mesh with "Failed to get collateral" or an MRTD/RTMR mismatch after a routine image/TCB update, and nodes disagree on the same peer.

### V3 — Bootstrap chicken-and-egg + unverified genesis
**Story.** Node #3 boots, gets its quote, submits `proposeMember`, then stalls forever. To be admitted, a majority must DCAP-verify it over the "RA-TLS handshake" — but dstack's `ra-tls` is X.509-cert plumbing only (`cert.rs`/`kdf.rs`): it embeds a quote in a cert; it has no listener/transport/rendezvous. The only member-to-member transport is `peer_grpc` (header: reachable "only over attestmesh0" wireguard — gated on already being verified), and member endpoints travel as `PeerEndpoint` over encrypted member-only `MessageFacet`. So a non-member has no address to send its quote to and no tunnel to send it through; admissions dry up. Meanwhile the cluster that did form is rotten at the root: member #1 entered via owner `genesisAdmit` with zero peer verification; at N=1 it *is* the whole majority, so it admits accomplice #2, the two admit #3, and "majority-attested" was never true — no honest peer ever checked the founder.
**Assumption.** That "verify each other over RA-TLS" is a usable bootstrap primitive — i.e. a not-yet-member already has a reachable authenticated channel to its vetters, and owner-fiat genesis is a safe stand-in for verification.
**Warnings.** No transport for the attestation exchange is named anywhere (ra-tls = no listener, peer_grpc = wireguard-only, PeerEndpoint = member-only); in any N≥1 test a fresh `proposeMember` accrues zero `voteAdmit`s, and no test ever DCAP-verifies the genesis node.

### V4 — Correlated TCB-recovery mass-eviction + griefing oscillation
**Story.** Intel publishes a TDX-module recovery (a new advisory, reclassifying the TCB level). Within one PCCS refresh every node's `dcap-qvl` returns `tcb_status: "OutOfDate"` instead of `"UpToDate"` (the status comes from Intel's collateral — identical for all identically-imaged peers, not node-local). The on-chain policy lists `UpToDate` as the only acceptable status, so at the next re-attestation every member fails every peer and files `voteEvict` against everyone; evictions cross `>50%` near-simultaneously and `memberCount` collapses below quorum in one block-span — the cluster wedges, and break-glass can't re-admit, so it's dead, not paused. Separately, near the 50% line eviction's symmetry oscillates: a node with a GC pause / PCCS hiccup / reboot is briefly slow, peers open `voteEvict`, the smaller majority evicts more, the recovered node re-proposes and re-lags — the set never settles.
**Assumption.** That re-attestation failure is independent and node-local, so symmetric `>50%` eviction safely "removes the one bad node" — when `tcb_status` is a globally-shared Intel-controlled input that flips correlated across the homogeneous fleet at once.
**Warnings.** A spike in `voteEvict`s clustered in time all citing the same fresh advisory / `tcb_status` transition; `memberCount` saw-tooth churn (repeated propose→admit→evict of the same `memberId`s) with reason "unreachable/timed-out re-attest" rather than "measurement mismatch."

### V5 — O(N) admission + coupling to the still-broken F2 transport
**Story.** Past a handful of nodes, admission grinds to a halt: every join needs a strict majority of the *full* set to each DCAP-verify the newcomer and land a `voteAdmit` UserOp. At N=15 that's 8 nodes all awake, un-rate-limited, not mid-reboot, not already verifying someone else — per join; real clusters churn (TCB reboots, timed re-attest, propose/evict), so wall-clock is dominated by overlapping ceremonies, each blocked on the slowest quorum member. Slow eviction keeps `memberCount` inflated, *raising* `floor(N/2)+1` — a feedback loop worsening with size. And none of the votes land anyway: they're EIP-4337 UserOps through `bundler.rs::submit`, which (lines 63-69, confirmed) signs the userOpHash while `paymaster` is empty; Alchemy inserts `paymasterAndData` after, so `validateUserOp` recovers a different signer and rejects every op (premortem F2). Until F2 is fixed, zero votes land, no quorum forms, member #2 is never admitted — and even after, every vote funnels through one Alchemy bundler + the webhook, a censorable chokepoint for the whole control plane.
**Assumption.** That per-event, all-member majority on-chain voting is cheap and reliable, and that the gasless UserOp transport it rides on works.
**Warnings.** A 3–5-node rehearsal where `proposeMember` never reaches `>memberCount/2` because a node is offline or its `voteAdmit` returns `AA24 signature error` (the F2 reject); median pending-admission latency climbs with size and `memberCount` drifts above the live node count (dead-node prune votes can't assemble quorum either).

### V6 — Strategic: the chain verifies nothing → "Safe + a message board"
**Story.** §1's "provable membership anchored to an attestation chain *the cluster contract verifies*" and the Join invariant ("present, to an installed attestor facet, a valid proof") die — under v2 the contract verifies nothing; peers do. §4.1's attestor-facet "three checks" evaporate; the facet is a registry + an allowlist nobody on-chain reads. What remains is AttestFacet (registry), MessageFacet (relay), NetworkFacet (key bulletin), and a vote tally — each a thing a Safe or a coordinator service already does. The fatal question is now unanswerable: real security = off-chain DCAP + honest-independent majority, both invisible to the chain; the chain can't see whether a voter actually ran DCAP (the quoteHash is self-asserted in the vote), can't tell honest from colluding signers, can't enforce verifier independence — it only orders votes and stores ciphertext. A Postgres coordinator with the same Safe-style multisig gives identical guarantees, cheaper. Fix #1 collapsed into DstackApp; fix #2 collapses into "Safe + bulletin board," with the one defensible on-chain property (independent attestation verification) explicitly removed.
**Assumption.** That a public chain adds value by *holding* attestation-derived state, when its only defensible value is *independently verifying* something no single trusted party could be trusted to verify.
**Warnings.** In review, "why not a Safe + a coordinator service?" is answered operationally (uptime/censorship) rather than "the chain verifies attestation no operator is trusted to"; the MessageFacet/Indexer/paymaster stack's only consumers are members who already share a mutually-DCAP'd wireguard mesh and could exchange the same bytes peer-to-peer — the chain is redundant to its own data plane.
