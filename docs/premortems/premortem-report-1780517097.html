Premortem — Deploying the dstack auth extraction

It is 3 months from now. We deployed the real KMS-chain verification preimages + the F2 sponsor-then-sign fix to a real owner-gated dstack cluster — and it failed. Working backward to find out why.
8 parallel investigators · target: dstack-auth-extraction (commits 1217c8c / c8635c7 / f316480 / 58fe26f) · 2026-06-03

Synthesis — read this first

Most likely failure

The cluster never reaches one member. Bring-up dies at first boot on the confirmed isAppAllowed deadlock; and patched past it, the never-validated codeId / preimage / KMS-signer assumptions revert registration next.

Every one is near-certain — not because they're bugs, but because they're untested interfaces. Nothing was ever run against a real KMS.

Most dangerous failure

Silent admission of unattested software. Compose-hash enforcement was removed from registration and moved to a gate that is deadlocked and absent from the signed proof.

The operator who flips allowAnyDevice to escape the bring-up deadlock removes the last on-chain binding of "approved image" → "member." CI stays green; the attestation guarantee is void.

The hidden assumption — named by nearly every investigator

Internal self-consistency was mistaken for external truth. The proof producer (MockKmsChain) and the verifier (DstackSigChain) are built from the same ported source, so "22+33+65 green" proves only that the implementation agrees with itself — not that it conforms to a real dstack KMS, a real app_id, a real bundler, or a real boot gate. No byte ever crossed the trust boundary.

⚠ Not hypothetical. Investigator C found the source project hit this exact error: the dstackgres tree carries a corrective Safe bundle monitor-kms-fix-root-signer.safe.json — they shipped the wrong allowedKmsRoots address (0x7b7d98a9… vs the real 0x52d3CF51…), bricked CVM boot, and needed an on-chain fix + a recover_root CLI. AttestMesh inherited the math, not the scar tissue.

The revised plan

  1. Capture one real proof first — it adjudicates A, B, and C at once. Stand up a single real dstack CVM on testnet; capture its KMS sig-chain material, real app_id, and real KMS root pubkey; check it in as a fixture; add a test that runs that fixture through DstackSigChain.verify. Until it passes, treat the verifier as unverified.
  2. Fix the isAppAllowed deadlock now, not as a follow-up. Check an owner-seeded allowedAppIds (the operator's flow step 1) or isOurMember(appId) instead of prior registration. Add a positive-path test: gate returns (true,"") for an allowlisted-but-unregistered appId.
  3. Wire the bundler into run() and land one real sponsored dstack_register on testnet (real Alchemy policy, real ClusterMember dummy-sig, real response parsing). One included UserOp with no AA24 is the only thing that validates F2.
  4. Add a cross-language ABI conformance test. Emit the sidecar's actual calldata (alloy 0.8), assert the selector == 0x537d491c in Rust, and decode those exact bytes back into the same proof in Solidity.
  5. Settle the compose-hash trust model explicitly. Either re-add an on-chain compose binding at registration, or document the observed KMS behaviour that makes gate-only enforcement safe — never an unobserved assumption. Decide the allowAnyDevice posture.

Pre-launch checklist

  • A real captured dstack proof fixture verifies through DstackSigChain.verify in CI (not a synthesized one).
  • isAppAllowed returns (true,"") for an allowlisted, not-yet-registered appId — and a real CVM boots past the gate on a cold cluster.
  • One real sponsored dstack_register UserOp is included on testnet (no AA24), with BundlerClient wired into run().
  • The sidecar-emitted selector is asserted == 0x537d491c in Rust and round-trip-decoded in Solidity.
  • Documented + observed proof that an unapproved compose hash cannot obtain a KMS-issued key for the codeId — or registration re-adds a compose binding. allowAnyDevice posture defined.

HighA — Non-canonical preimages (closed loop relocated, not eliminated)

The three preimages DstackSigChain.verify reconstructs were transcribed from TeeSQL/dstackgres, a Postgres-fused third-party adaptation — not canonical upstream dstack. A real CVM's KMS signed over a different domain/field layout (and the derived key over a different purpose than the placeholder "app-key"), so ECDSA.recover returned an address matching neither the allowlisted root nor the app pubkey. Every node reverted InvalidSigChain; zero members registered. CI was green because MockKmsChain.buildProof builds its preimages with the exact bytes verify checks — it even imports the library's own bytesToHex. The "literal drift guard" pins the implementation to itself.

Underlying assumption
A test suite whose proof producer and verifier derive from the same source can validate conformance to an external signing format neither was checked against.
Early warning signs

No proof fixture captured from a real KMS exists — every vector is vm.sign over in-repo preimages, and purpose is still "app-key". The cited source of truth is /tmp/dstackgres.

HighB — app_id ≠ member contract address (CodeIdMismatch)

The operator deploys a ClusterMember at 0xMEMBER and provisions a CVM "with the member address as its app ID." But dstack assigns app_id at app-registration (a function of the compose hash and the registration tx) — it isn't operator-dictated. The CVM's derive_key returns a codeId that is never bytes20(0xMEMBER), so dstack_register reverts CodeIdMismatch — every node, every time. The mock hid it by setting proof.codeId = bytes32(bytes20(memberContract)) by construction. dstackgres's DstackMember is the AppAuth contract dstack knows — a topology where codeId-equals-contract can hold — but AttestMesh's EIP-4337 ClusterMember is a different contract. No operator knob fixes it; app_id is bound upstream.

Underlying assumption
A dstack CVM's app_id is an operator-chosen value settable equal to the ClusterMember address, rather than an identifier dstack derives at app-registration time.
Early warning signs

The dstack app-registration step (or first derive_key) returns a codeId ≠ bytes20(memberContract). A fixture that defines the property under test is the smell that no captured proof exists.

HighC — KMS signer never matches the allowlisted root · real precedent

The operator seeds allowedKmsRoots from the published KMS pubkey; a real CVM boots and dstack_register reverts InvalidSigChain — the recovered signer isn't in the set. This already happened in the source project: monitor-kms-fix-root-signer.safe.json records a wrong root (0x7b7d98a9… vs 0x52d3CF51…), bricked boot, and a corrective tx + recover_root CLI. The silent branch is worse: an operator who "fixes" the revert by allowlisting whatever address the first proof recovers anchors trust to an unverified key. If the signer is app-scoped/intermediate or rotates, it becomes a recurring cluster-wide outage with no off-chain recovery (the chain is the sole source of membership).

Underlying assumption
The address ecrecover yields from a live KMS signature is a single, static, correctly-derivable value the operator can allowlist in advance.
Early warning signs

A real CVM's first registration reverts InvalidSigChain while forge test is green. The runbook has a manual "derive the KMS root from the pubkey" step with no on-chain assertion that derived == recovered.

CriticalD — isAppAllowed boot deadlock bricks bring-up

The KMS queries isAppAllowed at boot; compose and device pass, then memberIdOf[appId] == 0 → (false, "appId not a cluster member"). The KMS withholds the derived key; derive_all blocks, never builds a proof, never registers — so the next boot fails identically. The cluster never reaches one member. CI was green because the suite encodes the deadlock as expected: dstack_register is called directly (bypassing the gate), and the gate tests use a phantom appId (0xBEEF) that only exercises the compose branch (checked first). test_removeComposeHashBlocksBootGate asserts only that the reason is not "compose hash not allowed" — it never asserts the gate returns true, because with an unregistered appId it never can.

Underlying assumption
isAppAllowed's green tests meant the gate worked — but they only ever asserted rejection, never the cold-start accept path a real first node must traverse.
Early warning signs

No test asserts isAppAllowed(...) == (true,"") for a not-yet-registered appId. The first real CVM's KMS log shows isAppAllowed → false: "appId not a cluster member" while memberIdOf[appId] reads zero — visible before any tx.

CriticalE — Compose-hash enforcement regression (silent security failure)

DstackProof carries no composeHash/deviceId/tcbStatus field — registration is structurally incapable of constraining which image ran. verify checks only that an allowlisted root signed "dstack-kms-issued:" ‖ codeId ‖ appPubkey, that the app key authorised a derived key, and that the derived key signed the binding. A KMS root issues keys under a codeId; it does not, in the signed material, attest the compose hash. An attacker (or an operator running a patched build, or one who flipped allowAnyDevice to escape the deadlock) boots a tampered image under the same codeId, gets a normally KMS-issued derived key, registers — joins, pulls the CSK, receives plaintext peer traffic. The gate meant to bind compose-to-boot is a separate, deadlocked view never invoked at registration.

Underlying assumption
An allowlisted KMS root having issued a key under a codeId cryptographically implies the approved compose hash booted — when the signed chain binds neither.
Early warning signs

A live member's running image hash matches no allowedComposeHashes entry, yet its memberId is live. isAppAllowed observed false at real boot while registrations still succeed.

HighF — F2 fix unwired + untested against a live bundler

F2 shipped green — but only against a hand-written sample_sponsorship() JSON the author also wrote. BundlerClient::new is invoked nowhere in the tree, and its only consumer (AgentService::new) is itself never called. state::run() derives keys, discovers the cluster, sets Phase::Registering, then serves health and returns — build_register_calldata is dead. A real zero-ETH node sat in "registering" forever. Hand-wired to debug, the live Alchemy path broke as suspected: modelled on dstackgres's LightAccount v2, but AttestMesh's ClusterMember has a different validateUserOp; the hardcoded dummy sig mismatched verification gas, response field names didn't match the exact-key parser (which bail!s on any missing key), and GAS_POLICY_ID empty-by-default sent policyId: "".

Underlying assumption
A unit test passing on self-authored fixture JSON proves an integration works, and code that compiles is code that runs in the bring-up path.
Early warning signs

A node logs phase=registering indefinitely with no eth_sendUserOperation leaving the box. BundlerClient::new / build_register_calldata have zero call sites reachable from run().

MediumG — Cross-language ABI / selector drift

Three independent DstackProof ABIs shipped green: the webhook hard-codes 0x537d491c (viem), the contract's selector came from solc, the sidecar's from alloy 0.8's sol! — none compared byte-for-byte. The sidecar's only relevant test asserts bind_hash (a keccak over static params), nothing about the selector or proof calldata. The trap sprang at first real registration because the encoders are unwired, so no encode→decode ever ran. With five dynamic bytes + a trailing string, an off-by-32 head offset or differing field order yields a 4-byte prefix the webhook never allowlisted (sponsorship silently denied) — or, selector matching but tail differing, the facet decodes garbage and reverts inside verify after the node paid gas.

Underlying assumption
Three per-language suites each passing in isolation proves the three ABIs agree — when no test compares one component's actual bytes/selector against another's.
Early warning signs

0x537d491c appears only in webhook code; grep returns zero hits in sidecar/ and contracts/. The encoders have no caller reachable from run().

HighH — "IMPLEMENTED + green" mistaken for deploy-ready

The status line — "IMPLEMENTED, 22+33+65 tests green, fmt/clippy clean" — is what traveled to standup, the demo, the partner deck. Nobody re-read the Open Questions three scrolls down, where the spec itself confessed no captured proof, no confirmed purpose, and no working boot gate existed. The deferred items lived in prose; the checkmarks lived in the status line, and stakeholders read the status line. First boot bricked on the deadlock; patching it open then surfaced the never-captured-proof and placeholder-purpose risks. These were never code bugs found late — they were the actual gating work, mislabeled as follow-ups.

Underlying assumption
"All tests pass" measures real-world readiness — when the tests only verified the system against a mock the team authored, and the spec had already named the three unknowns it couldn't cover.
Early warning signs

The "IMPLEMENTED" status and the Open Questions contradict each other in the same document, and no issue/gate/checklist tracks the deferrals. Zero CI artifacts reference a real KMS, a testnet CVM, or a live Alchemy call.
