Premortem — the FIX (dstack-registration-rework)

We premortemed the drafted fix itself. Frame: it's months from now, we built it exactly as specced, and it failed.

This premortem killed the plan. The fix as specced fails on ≥3 certain technical dimensions (P2, P3, P4) and is strategically self-defeating (P1+P6). The architecture decision it encodes — adopt dstack's allowlist-gate model, trust the KMS off chain — should be revisited before any code is written.
What
A rework that on chain verifies one real dstack KMS signature + an allowlist on proof-supplied fields + a pubkey binding, trusting the dstack KMS for the quote; sidecar rewritten to prpc with encrypted-disk CSK persistence. Both ends of the registration seam.
Who
The team building the fix; operators/nodes who need registration to work AND be secure.
Success
A real dstack CVM registers by verifying a real proof; the model is sound; the sidecar talks to the real guest agent; the CSK survives restarts.
Method
6 parallel investigators, each grounded in the spec + the real dstack source (kms contracts, kms/src/crypto.rs + main_service, guest-agent + ra-rpc, basefiles, attestation.md). 2026-06-03.

Synthesis — read this first

Most likely failure

P2 — dstack's app-key / app_id model doesn't map to per-member identity (and it's certain).

dstack's get_app_key takes app_id from the verified TDX quote's boot_info, not from the caller, and only issues keys to apps in DstackKms.registeredApps gated by allowedOsImages. Using arbitrary ClusterMember addresses as app_ids means the KMS returns "App not registered" and refuses to issue a key — registration can't start. Run members under one registered app and derive_k256_key(parent, app_id) hands every instance the same key → identical EIP-4337 owner → the second dstack_register reverts duplicate. The spec's central assumption ("the KMS will sign a unique key for our chosen app_id") is false.

Most dangerous failure

P1 + P6 — the fix is both insecure and self-defeating.

dstack's dstack-kms-issued signature binds app_id+pubkey only, not the compose hash. The gate checks proof.composeHash, a self-asserted field — so a holder of any KMS-issued key registers while claiming an allowlisted hash but running unapproved software. That makes §9's "approved software" guarantee fictional, and P6 shows it simultaneously guts the thesis: §1's "anchored to an attestation chain the cluster contract verifies" and §10's "verifier as facet" both go false, leaving DstackFacet ≈ dstack's own DstackApp.isAppAllowed + a registry. The review question "why not just deploy DstackApp + a messaging contract?" has no answer. The fix could pass every test and still lose.

The hidden assumption

That the attestation-verification layer is swappable plumbing.

The fix assumes AttestMesh could "adopt dstack's model" cheaply. But the chain independently verifying attestation is the reason AttestMesh exists. Decision B (trust the KMS off chain) negotiates away the anchor — the spec's own Open Question 2 and Non-Requirements already admit it. Swapping the verifier for a trusted-KMS gate doesn't simplify the project; it deletes its differentiator.

The revised plan — revisit the architecture before writing code

  1. Do not implement the spec as drafted. The premortem invalidates Decision B on security (P1), strategy (P6), and feasibility (P2).
  2. Stand up a real dstack CVM + KMS first and answer empirically — these gate everything: can the KMS issue a key for an AttestMesh-controlled app_id, or must each member be a registered dstack app? What's actually in the TDX quote's report_data? Is the rootfs ephemeral (it is — dm-verity) and where is the LUKS data disk?
  3. Reconsider per-instance, quote-based binding. The master spec's original rule (§4.1) binds xPub‖wgPub into the TDX quote's report_data — per-instance, sidesteps the per-app-key collision (P2), and (if the quote is verified on chain or by an on-chain DCAP/verifier) preserves the "chain verifies attestation" thesis (P6). Re-evaluate the on-chain-quote path the draft deferred as the primary, not the fallback.
  4. Implementation facts now fixed (any architecture): the dstack client must speak prpc/ra-rpc over HTTP/1 (Rocket, POST /prpc/Service.Method), not tonic gRPC (P3); CSK persistence targets the LUKS data disk (/dstack), not the verity rootfs (P4); the real-proof capture needs an owner + provenance metadata + ≥2 captures to diff (P5).

Pre-implementation checklist

  • ☐ A real dstack CVM+KMS exists; we've confirmed whether/how it issues a signed key for an AttestMesh app_id (P2).
  • ☐ We've dumped a real GetQuote and inspected report_data + the k256_signature_chain layout + where tcb_status lives (P5/P1).
  • ☐ The architecture decision (on-chain quote/report_data binding vs trust-KMS) is re-made with those facts, security + thesis implications written down (P1/P6).
  • ☐ A throwaway prpc round-trip from the sidecar to a real guest agent succeeds before any contract work (P3).
  • ☐ A reboot test confirms the CSK survives on the data disk, or the originator re-derives without local state (P4).

The six failure modes

P2 · dstack app-key/app_id model doesn't map to per-member identity

Certain
KMS get_app_key derives app_id from the verified quote, not the caller, and only signs for apps in DstackKms.registeredApps. Ad-hoc ClusterMember app_ids → "App not registered" (no key issued). Under one registered app, derive_k256_key(parent,app_id) gives every instance the same key → identical owner → duplicate-member revert. Per-instance uniqueness lives in instance_id (disk key only), never in the anchored k256 app key.
Underlying assumption
The KMS will derive and sign a unique k256 key for an arbitrary app_id we choose.
Early warning signs
DeriveK256Key returns "App not registered" for unregistered members; two members on one image share appKeyAddr and the 2nd register reverts.

P1 · composeHash is self-asserted (the gate binds nothing)

Certain
dstack's sign_message hashes [prefix, ":", app_id, sec1_pubkey] — the compose hash is not in the signed bytes. The gate checks proof.composeHash, a string the registrant typed. Anyone holding a KMS-issued key for their app_id pastes in an allowlisted hash, signs the binding, and registers while running unapproved software. The chain never saw the quote that measured the software.
Underlying assumption
Recovering one KMS sig over app_id+pubkey transitively authenticates the separately-supplied composeHash.
Early warning signs
Registration succeeds where proof.composeHash ≠ the registrant's own Info→AppInfo hash; the replay fixture signs a synthetic preimage with a free composeHash → green CI, zero binding.

P3 · prpc ≠ gRPC — tonic can't talk to the guest agent

Certain
dstack's guest agent is Rocket (HTTP/1.1) serving POST /prpc/<Service>.<Method> with protobuf-or-JSON bodies, Content-Type: application/json — dstack's own ra-rpc, consumed by prpc_build, not tonic-build. A tonic client speaks HTTP/2 gRPC framing; the connection fails before any RPC. The team rediscovers the original "guessed the protocol" failure one layer down: the .proto pins the messages, not dstack's transport.
Underlying assumption
A .proto with service/rpc blocks implies gRPC/HTTP-2, so tonic codegen interoperates.
Early warning signs
dstack's ra-rpc/SDK imports rocket/reqwest/prpc and zero tonic/h2; the first live call dies with an h2 framing error while the same messages round-trip against a tonic mock.

P4 · CSK persistence targets ephemeral rootfs → restart deadlock

High
dstack's rootfs is rootfs.img.verity (dm-verity, read-only, measured into RTMR2). Durable state is a separate LUKS volume mounted at /var/volatile/dstack/persistent → /dstack. ${STATE_DIR}/csk on the rootfs is volatile, so every restart wipes the onboardee's CSK; the restart path always re-pulls; re-pull needs a live tunnel that a cold boot lacks → stuck at pulling-csk forever (F6 on every reboot). The originator's seal/unseal still call nonexistent dstack RPCs.
Underlying assumption
${STATE_DIR} / "the dstack-encrypted rootfs" is durable across restarts.
Early warning signs
Post-reboot, ${STATE_DIR}/csk is missing and the agent re-pulls every boot; mount shows it on an overlay/tmpfs, not under /dstack.

P5 · captured-proof fixture: unowned dependency + single-version snapshot

High
Capturing a real proof needs TDX hardware + a deployed KMS + on-chain DstackApp wiring — an "infra prerequisite" nobody owns, so the one gating test is un-runnable and the engineer re-guesses Open Question #1, reproducing the original F1 bug. Once captured, the fixture freezes one CVM's bytes: k256_signature_chain is a 2-element vector whose layout can shift, tcb_status lives inside the tcb_info JSON (not a proto field), TCB status varies by platform/date, KMS roots rotate → green CI, red on a real newer CVM.
Underlying assumption
One captured proof is a stable spec of "a real dstack proof," not a single sample of a versioned, time-varying distribution.
Early warning signs
The fixture lands with no provenance (dstack SHA, proto version, KMS root, TCB date) and no second capture to diff; the "stand up a CVM/KMS" ticket has no assignee.

P6 · strategic inversion — the fix guts AttestMesh's reason to exist

Strategic
Adopting dstack's model makes DstackFacet ≈ DstackApp.isAppAllowed + a pubkey registry, and the fatal adopter question — "why not just deploy DstackApp + a messaging contract?" — has no answer. §1's "attestation chain the cluster contract verifies," the Join invariant, and §10's "verifier as facet" all become false. The project demos but can't sell; adopters fork the two dstack primitives and route around it. The thesis dies from redundancy, not a bug.
Underlying assumption
AttestMesh's value is the messaging/mesh surface, so the verification layer can be swapped for a trusted-KMS gate.
Early warning signs
The spec's own Open Question 2 + Non-Requirements punt independent verification; a reviewer diffs dstack_register against DstackApp.sol and sees the same gate + registry.
