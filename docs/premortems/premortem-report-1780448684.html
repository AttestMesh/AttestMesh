Premortem — Deploying the AttestMesh v1 Cluster

Frame: it's a few weeks from now. We deployed the three-node demo on Base Sepolia and it failed. This is why it died.

v2 · re-grounded against the actual dstack source (dstack-tee/dstack) ≥3 independent certain showstoppers gate registration alone
What
The AttestMesh v1 three-node demo on Base Sepolia: infra → Indexer → gas-webhook/paymaster → ClusterDiamond → 3 ClusterMembers → 3 dstack CVMs that register, mesh, distribute the CSK, and go healthy.
Who
The AttestMesh org (infra + Indexer + paymaster) and three node operators. This demo is the end-to-end proof.
Success
All 3 register on chain, the wg mesh converges, the CSK reaches all 3, every healthcheck returns 200, app containers start.
Method
7 failure modes, the dstack-touching ones re-grounded in the real dstack repo (KMS contracts, kms/src/crypto.rs, guest-agent/rpc/proto/agent_rpc.proto, basefiles). 2026-06-03.

What the dstack source changed

Reading the real dstack code sharpened two failures and downgraded one

  • F1 — sharpened to an exact, documented mismatch. dstack does no on-chain signature verification (DstackApp.isAppAllowed is a pure allowlist gate); it signs keccak256("dstack-kms-issued" ‖ ":" ‖ app_id ‖ sec1_pubkey) off chain (kms/src/crypto.rs). AttestMesh verifies an invented keccak256(abi.encode("dstack.app", appKey, composeHash)) chain on chain — a different domain, encoding, fields, and level count. A real proof cannot verify.
  • F4 — sharpened. The guest agent is prpc/protobuf (GetKey{path,purpose,algorithm}, DeriveK256Key, GetQuote), not JSON /DeriveKey; and there is no Seal/Unseal — persistence is the encrypted rootfs.
  • F3 — DOWNGRADED from certain to low. dstack CVMs do ship wireguard (/etc/wireguard/*.conf, gateway wg.conf); the "no wireguard at all" premise was wrong.
  • A positive: AttestMesh's IAppAuth.AppBootInfo + isAppAllowed mirror dstack exactly — the boot-gate side is correct. The team mirrored what was visible in dstack's contracts and invented what lives in its Rust.

Synthesis

Most likely / clearest failure

F1 — the on-chain registration verifier checks a signature format dstack never produces.

Not a tuning bug: DstackSigChain + dstack_register were authored without reading dstack/kms/src/crypto.rs. dstack signs keccak256("dstack-kms-issued:" ‖ app_id ‖ sec1_pubkey) (recoverable, off chain) and does only an allowlist check on chain; AttestMesh recovers an abi.encode("dstack.app", appKey, composeHash) preimage that has no counterpart in dstack. Every real CVM reverts at KmsAppKeySigInvalid. With F4 (the client can't even speak prpc) and F2 (the UserOp can't validate), three certain showstoppers gate registration before a single member exists.

Most dangerous failure

CSK persistence built on a primitive dstack doesn't have (F4) against an immutable on-chain commitment.

seal/unseal don't exist in dstack. The originator can re-derive the CSK deterministically, but an onboardee that pulled it has nowhere durable to put it under the current design — while its keccak256(CSK) commitment is already immutable on chain. A naive "derived something, commit it" path can strand the cluster with a committed-but-unrecoverable key. Persist to the encrypted rootfs or re-pull on restart — by design, not as an afterthought.

The hidden assumption (sharpened)

The team read dstack's contracts and invented dstack's Rust.

AttestMesh mirrored IAppAuth.AppBootInfo and isAppAllowed exactly (they're in .sol files) — but invented the guest-agent protocol and the KMS signature format (which live in dstack's Rust: agent_rpc.proto, crypto.rs), then validated the inventions with mocks that encode the same inventions. The boundary of what was actually read from dstack is precisely the boundary between what works and what is fictional.

The revised plan (dstack-concrete)

  1. dstack client → prpc. Generate from agent_rpc.proto (or use dstack's SDK): GetKey{path,purpose,algorithm}, DeriveK256Key, GetQuote{report_data}, Info. Drop seal/unseal: re-derive the originator CSK deterministically; persist the onboardee CSK to the encrypted rootfs (or re-pull on restart).
  2. Re-architect the verifier (F1) — choose deliberately: (a) match dstack on chain — recover keccak256("dstack-kms-issued:" ‖ app_id ‖ sec1_pubkey) against an allowlisted KMS k256 address, binding compose-hash→app_id→member via dstack's app registry / the quote; or (b) adopt dstack's model — off-chain KMS verifies the quote, on chain you only run isAppAllowed (simpler, but reintroduces a trusted off-chain attestor — a real decision for "the chain is the source of truth").
  3. Capture a real proof. Pull one live DeriveK256KeyResponse + GetQuote from a real dstack CVM; add a forge fork-test replaying it against DstackFacet. Highest-value single validation; blocks deploy until green.
  4. F2: reorder bundler.rs::submit to sponsor-then-sign; land one real UserOp on Sepolia.
  5. F5: implement the Indexer event_data RLP decode + dispatch; anvil test A→B peer config.
  6. F3: confirm the sidecar container has NET_ADMIN + wg/ip; remove the .ok() swallow (downgraded, not dismissed).
  7. F6/F7: fix the originator race (order by MemberRegistered block+logIndex), rehearse 3-node on anvil, add per-phase health detail + a runbook.

Pre-deploy checklist

  • ☐ A forge fork-test replays a real k256_signature_chain + quote against DstackFacet and passes (F1).
  • ☐ A prpc GetKey/DeriveK256Key round-trips against a real guest agent (F4).
  • ☐ One sponsored registration UserOp lands on Sepolia and emits MemberRegistered (F2).
  • ☐ A's PeerEndpoint configures a wg peer on B in an anvil integration test (F5).
  • ☐ 3-node all-healthy once on a local harness, with the CSK persisted/re-derived across a restart (F4/F6).

The seven failure modes (dstack-re-graded)

F1 · On-chain verifier checks a signature dstack never produces▲ sharpened

Certain
dstack signs keccak256("dstack-kms-issued" ‖ ":" ‖ app_id ‖ sec1_pubkey) (recoverable, off chain; kms/src/crypto.rs) and does only an allowlist check on chain (DstackApp.isAppAllowed). AttestMesh recovers keccak256(abi.encode("dstack.app", appKey, composeHash)) — different domain, encoding, bound fields, and level count. Real k256_signature_chain can't recover → dstack_register reverts for every node. The mock encoded AttestMesh's own invention, so 17 tests pass while reality fails.
Underlying assumption
dstack emits an abi.encode-shaped, compose-hash-committing, 3-level chain verifiable on chain — when it signs a raw-concat preimage off chain and only allowlist-checks on chain.
Early warning signs
A fork-test on a real proof reverts; DstackSigChain's "dstack.app" string appears nowhere in dstack/kms/src/crypto.rs.

F2 · EIP-4337 signature dies once Alchemy inserts paymaster data— unchanged

Certain
bundler.rs::submit signs the userOpHash while paymaster==None; Alchemy fills paymasterAndData after the webhook approves; the EntryPoint recomputes the hash, validateUserOp recovers a different signer, and every registration op reverts (AA24). The sidecar treats it as transient and retries forever. Now coupled to F1: the binding key is a dstack k256 key whose provenance proof is the same broken chain.
Underlying assumption
A signature computed before paymasterAndData is populated still validates afterward.
Early warning signs
AA24 signature error on every registration; no test asserts hash equality across the paymaster handshake.

F3 · Wireguard on the real CVMs▼ downgraded

Low
dstack CVMs ship wireguard (rootfs /etc/wireguard/*.conf; gateway wg.conf), so the "no module/binaries" premise was wrong — this is no longer a guaranteed showstopper. Residual risk: AttestMesh's second attestmesh0 interface still needs NET_ADMIN + wg/ip reachable in the sidecar's container, and state::run still .ok()-swallows create_interface failures, so a real problem would be silent.
Underlying assumption
The dstack CVM has no wireguard (it does).
Early warning signs
Residual: the .ok() swallow + whether the app container is granted NET_ADMIN.

F4 · dstack client is the wrong protocol + assumes a nonexistent seal▲ sharpened

Certain
UnixSocketDstack POSTs JSON /DeriveKey with {"path":purpose,"purpose":subkey}; real dstack is prpc/protobuf (GetKey{path,purpose,algorithm} / DeriveK256Key / GetQuote) — wrong protocol, method, and field mapping; the first call fails. And seal/unseal don't exist — the sidecar's dstack.seal(...) calls a nonexistent RPC; persistence is the encrypted rootfs. The originator can re-derive (deterministic GetKey); onboardees must persist to disk or re-pull.
Underlying assumption
dstack exposes a JSON HTTP /DeriveKey + a seal/unseal RPC; in fact it's prpc and persistence is the encrypted disk.
Early warning signs
No test instantiates UnixSocketDstack; grep -r Seal dstack/guest-agent returns nothing; a prpc client from agent_rpc.proto shows the mismatch immediately.

F5 · Sidecar verifies Indexer pushes but never decodes/acts on them— unchanged

Certain
connect_and_run verifies the push signature, tracing::debug!s, and ends at let _ = &shared;. The RLP event_data decode/dispatch is a TODO, so MessageSent never becomes a PeerEndpoint and wg::add_peer is never called. Registration succeeds, the stream looks healthy, every signature verifies — and ListPeers stays empty. The mesh's only learning mechanism is a no-op behind a green light.
Underlying assumption
"Signature-verified and logged" equals "consumed and acted upon."
Early warning signs
add_peer/handshake counters stay zero while verified indexer push climbs; no test drives connect_and_run.

F6 · Convergence + CSK distribution deadlock under real async timing— unchanged

High
Two nodes read memberCount() in the same block before either tx confirms — both see 0, neither becomes originator, all sit at pulling-csk forever. Even when one wins, the strict active == live gate never latches across staggered boots: the window slides faster than the last node joins, so the three views are never simultaneously equal.
Underlying assumption
A system validated only on a synchronized logical clock with all peers at t=0 behaves the same when three real nodes boot at independent wall-clock times.
Early warning signs
Two+ nodes read the originator before any MemberRegistered confirms; cskCommitment() stays 0x0; is_converged flaps by exactly the last-joined node.

F7 · Never integration-tested; every dependency a fail-closed SPOF— unchanged

High
Three sidecars wedge in different phases (A pre-registration, B subscribed-but-empty, C waiting on B), each silently at 503 with no signal of which dependency it's blocked on, no cross-node correlation, no orchestrator. The §16.2/§14.2 harnesses are #[ignore]d; the first real inter-process contact is in front of the audience. Green unit tests created false confidence exactly at the seams.
Underlying assumption
Components that pass their own unit tests compose correctly across seams on first contact, so end-to-end testing is a formality.
Early warning signs
CI has never produced a passing multi-process/anvil run; the components were authored by different agents with no shared seam contract.
