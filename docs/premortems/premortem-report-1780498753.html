Premortem — the EXTRACTION / PORT (dstack-auth-extraction)

We ported dstackgres as specced. Frame: months from now, it failed — not the design (it's proven), but the port.

Third fix attempt, third strong negative — verified in code with hard numbers: dstackgres's data-sidecar is 35,323 lines / 46 modules, 12× v1's sidecar; the CSK struct's wire fields are pg_replication_password/control_plane_key_hex; the two diamonds' pinned slot assertions detonate on contact; alloy 0.8 vs 1 is a major-version wall; and the mock hides the wrong verification preimages.
But this one converges the whole thread. Across all three fix premortems, the surviving answer is the same: keep v1's working scaffolding and surgically extract only the verification primitive (the ~200-line DstackSigChain + real preimages) — don't port the 35k-line system, and don't reinvent. See "the convergent fix" below.
What
Port dstackgres's auth code (teesql-group-auth + sqlx-ra-tls + data-sidecar + gas-payment) into AttestMesh, rebranded, dropping Postgres/control-plane/leader.
Who
The team doing the port; everyone downstream of a working dstack integration.
Success
A clean, finished port that passes against a real dstack proof and brings up a mesh.
Method
6 parallel investigators grounded in the spec + AttestMesh code + the dstackgres source. 2026-06-03.

Synthesis — read this first

Most likely / most immediate

E6 + E2 — the wholesale port can't even build.

dstackgres's data-sidecar is 35,323 lines / 46 modules (12× v1's 2,777); contracts 3,885 vs 1,556. The two diamonds are mutually exclusive: attestmesh.storage.Member (rich record, memberId=keccak256(abi.encode(cluster,member,attestorId)), EIP-4337 ClusterMember) vs teesql.storage.Member (just address cluster, memberId=keccak256(derivedPubkey), a UUPS-forwarder DstackMember). Namespaces.t.sol's slot assertions detonate; the two memberId formulas orphan every "surviving" lookup; first cargo build fails on alloy 0.8-vs-1 + missing workspace crates. Six weeks → a chimera that doesn't run, v1's tests now red.

Most dangerous

E3 — the rebrand silently breaks (or weakens) verification, and the mock hides it.

v1's facet already recovers over the wrong preimage (abi.encode("dstack.app",…)) vs dstack's real abi.encodePacked("dstack-kms-issued:", bytes20(codeId), appCompressedPubkey), and MockKmsChain was built to match the wrong facet — a closed loop where any preimage round-trips. A port that fixes the facet but not the mock passes CI and rejects every real proof; a Proof field-reorder maps bytes into kmsSignature/appCompressedPubkey and can recover attacker-chosen addresses while the mock still passes. "dstack-kms-issued:" has zero test coverage.

The hidden assumption

That dstackgres's auth is a separable, finished module you copy-and-rebrand.

It's a tightly-coupled subset of a system several times AttestMesh's size, fused to Postgres (the CSK ClusterSecrets carries pg_replication_password; cold_start_election takes &PgManager + reads WAL LSNs), on a different diamond, memberId algebra, member ABI, mesh/IP scheme (10.42.0.0/24 octet table vs 10.13.0.0/16 keccak), and toolchain (alloy 1).

The convergent fix (all three premortems)

Surgical extraction — not wholesale port, not reinvention.

  1. Port ONLY the verification primitive: DstackSigChain (real "dstack-kms-issued:" preimages + recover/compressedToAddress) — the ~200-line crown jewel v1 got wrong and dstackgres got right, self-contained. Replace v1's invented one + the dstack_register preimages.
  2. Fix the mock + add a real fixture: rewrite MockKmsChain to produce real-format proofs; check in a captured real dstack proof; test the literal "dstack-kms-issued:". Kills E3's closed loop.
  3. Fix F2 in v1's own bundler.rs (sponsor-then-sign), using dstackgres's gas_payment/alchemy.rs as a read-only reference — don't port across alloy 0.8→1 (avoids E4).
  4. Fix v1's remaining gaps AttestMesh-native (CSK→LUKS data disk; originator selection; encrypted-endpoint rendezvous over MessageFacet), informed by dstackgres but not importing its 35k-line modules (avoids E1/E5/E6).
  5. Do NOT graft two diamonds or port the data-sidecar wholesale (avoids E2/E6's chimera). Keep v1's diamond/MessageFacet/heartbeat/mesh-IP — they pass tests.
  6. Narrow the spec from "port 8 facets + a crate + 15 modules" to "extract the verification primitive + reference the rest."

The six failure modes

E1 · The extraction boundary isn't clean

High
The CSK (ClusterSecrets) is the Postgres envelope (pg_replication_password, backup_encryption_key_hex, control_plane_key_hex); group_auth/onboarding re-export it. cold_start_election takes &PgManager, reads WAL LSNs, calls leader_lease() — "election" = "elect the PG primary + claim the lease." On-chain CoreFacet shares CoreStorage across register/onboard/claimLeader. Drop the Postgres parts and the auth code stops working.
Underlying assumption
"auth/CSK/election" and "Postgres/leader/control-plane" are separable — they're the same code through shared structs.
Early warning signs
First port forces a yes/no on pg_replication_password in the CSK wire format; cargo build demands PgManager/wal_bearer_writer/boot_restore.

E2 · Two incompatible diamonds collide

Certain
Disjoint ERC-7201 regimes: attestmesh.storage.Member (full record) vs teesql.storage.Member (just address cluster); two memberId formulas; an EIP-4337 ClusterMember vs a UUPS-forwarder DstackMember with no 4337. "Keep base, replace core" assumed they compose — a diamond's real interface is its storage map + memberId algebra + member ABI, and on all three they're mutually exclusive.
Underlying assumption
A shared SolidStateDiamond base means two diamonds are compositionally compatible.
Early warning signs
Namespaces.t.sol slot assertions fail when a rebranded teesql.storage.Member lands; a ported member looked up by surviving code returns the zero record.

E3 · Rebrand silently breaks/weakens verification

Certain
v1 recovers over abi.encode("dstack.app",…); dstack's real preimage is abi.encodePacked("dstack-kms-issued:", bytes20(codeId), appCompressedPubkey). MockKmsChain mirrors the wrong facet → closed loop, any preimage round-trips. Fix the facet but not the mock → green CI, rejects every real proof. Reorder the Proof struct → recover attacker-chosen addresses while the mock passes. "dstack-kms-issued:" has zero coverage.
Underlying assumption
A green suite proves the verifier correct — it only proves it agrees with a mock built to mirror the wrong code.
Early warning signs
The "port DstackSigChain" PR leaves the mock/tests untouched; no test references "dstack-kms-issued:"; abi.encode(/"dstack.app" still in the post-port verifier.

E4 · "Proven" hides version skew + TODOs + dead upstream

High
alloy 0.8 vs 1 — a major signer/provider break; the ported gas_payment/dstack.rs won't compile or silently shift the userOpHash (reopening F2). Inherited TODO(future-kms-dispatch) hardcodes a single KMS adapter — fine in dstackgres, but it contradicts AttestMesh's pluggable-attestor "agnostic core" directive. TeeSQL's product is on hold → a frozen upstream, bugs and all.
Underlying assumption
"Proven in dstackgres" = "correct in isolation" — it meant "correct given its versions, context, and tolerated TODOs."
Early warning signs
First build fails on alloy 0.8-vs-1 trait mismatches; grep "TODO(future-kms-dispatch)" returns dstackgres markers verbatim in the ported tree.

E5 · Kept AttestMesh glue doesn't fit the ported mesh

High
Two endpoint protocols, two wg-pubkey publishers (NetworkFacet.publishWgKey self-asserted vs WgMeshFacet.setMemberWgPubkeyAttested quote-derived) that disagree → handshake never completes. Two subnets (10.13/16 keccak vs 10.42/24 octet table) → heartbeats land nowhere. Two liveness models (first-convergence vs fence_watchdog/degraded_mode assuming a leader v1 dropped) → neither reaches healthy.
Underlying assumption
Endpoint exchange, wg-pubkey publication, and liveness are mix-and-match — they're one coupled contract.
Early warning signs
Two CIDRs live in one tree; two wg-pubkey writers compile side by side and PeerEndpoint.wg_pub matches neither's on-chain value.

E6 · "Extraction" undersells a re-architecture that stalls

Certain
35,323 lines / 46 modules — 12× v1; "drop Postgres" = surgery on every file (group_auth 170 refs, onboarding 216, cold_start_election 89). The sidecar won't build (missing teesql-common); the diamonds never reconcile; alloy unhandled; two mesh models unwired. Six weeks → a chimera that doesn't run, v1's tests red, sunk cost keeping it limping.
Underlying assumption
dstackgres's auth is a separable finished module you copy and rename.
Early warning signs
First cargo build after copying a module fails on missing workspace crates + the alloy mismatch; the tree accumulates half-rebranded teesql_* beside attestmesh_*.
