## HIGH severity (fix before code generation)

### H1. Binding key derivation purpose string mismatch
The `dstack.derive_key` purpose used for the registration binding signer disagrees across specs. Mismatch would produce two different secp256k1 keys — the contracts would reject every CVM's binding signature.

- `docs/specs/teemesh-coordination-layer.md:179, :277` — `teemesh.bind.v1`
- `docs/specs/teemesh-coordination-layer.md:484` (§13 item 18) — `teemesh.binding.v1`
- `docs/specs/contracts.md:403` — `BIND_DOMAIN = "teemesh.bind.v1"` (used as the *message domain*, distinct from the derive-key purpose)
- `docs/specs/sidecar.md:138, :208` — `teemesh.binding.v1` (purpose) + binds to a `teemesh.bind.v1` *domain* string

The signed-message **domain string** consistently uses `teemesh.bind.v1` (contracts spec authoritative). The **derive-key purpose** is what's disagreeing — pick one and search-and-replace. Recommend `teemesh.binding.v1` for the derive purpose since that reads less easily as a typo of the domain.

### H2. `wgPublicKeyOf` vs `wgPubKeyOf` selector name
The view selector that returns a member's wireguard pubkey is spelled two different ways. The contracts spec uses `wgPubKeyOf` consistently; the master spec has one stale `wgPublicKeyOf`.

- `docs/specs/teemesh-coordination-layer.md:140` — `wgPublicKeyOf(memberId)` on NetworkFacet
- `docs/specs/teemesh-coordination-layer.md:112` — `wgPubKeyOf(memberId)` on AttestFacet (the convenience mirror)
- `docs/specs/contracts.md:183, :292` — `wgPubKeyOf` (both on `IAttest` and `INetwork`)

Pick the shorter form (`wgPubKeyOf`) for consistency with `xPubKeyOf` and the existing contracts spec.

### H3. ClusterMember characterized two incompatible ways in the master spec
§5 still describes ClusterMember as a "passthrough" UUPS proxy that "do not hold cluster state". §13 item 18 makes it a full EIP-4337 smart wallet (`IAccount` + `IAppAuthBasicManagement` + UUPS) that owns its k256 key, exposes `execute(target, value, data)`, and stores its own owner.

- `docs/specs/teemesh-coordination-layer.md:199-201` — old passthrough framing
- `docs/specs/teemesh-coordination-layer.md:484` (§13 item 18) — current smart-wallet framing

§5 needs a rewrite to match the new shape that contracts §9 already documents.

### H4. Binding key reuse contradiction (one-shot vs long-lived)
§4.2 and §9 say the dstack-derived k256 binding key is "used for this one signature and never again" / "no long-lived secp256k1 signing key exists on the CVM side". §13 item 18 explicitly installs it as the EIP-4337 wallet owner — i.e. signs every subsequent UserOp.

- `docs/specs/teemesh-coordination-layer.md:179, :404` — one-shot
- `docs/specs/teemesh-coordination-layer.md:484` — long-lived signing surface

Now that 4337 is in scope, the "one-shot" framing is wrong. Update §4.2 and §9 (Trust model) to acknowledge that the binding key signs every UserOp post-registration.

### H5. `dstack_register` arity disagreement
Master spec says 3 args, contracts spec says 4. The 4-arg version (adding `address memberContract`) is what the gas webhook's selector allowlist depends on.

- `docs/specs/teemesh-coordination-layer.md:179, :281` — `dstack_register(proof, xPubKey, wgPubKey)`
- `docs/specs/contracts.md:386-391` — `dstack_register(DstackProof proof, address memberContract, bytes32 xPubKey, bytes32 wgPubKey)`
- `docs/specs/gas-webhook.md:159` — selector for the 4-arg version

Update the master spec to match contracts.

### H6. `MessageFacet.send` argument order mismatch
Master spec puts ciphertext before envelopeId; contracts spec (and the gas webhook's selector entry) puts envelopeId before ciphertext.

- `docs/specs/teemesh-coordination-layer.md:128` — `send(recipient, bytes ciphertext, bytes32 envelopeId)`
- `docs/specs/contracts.md:253-257` — `send(bytes32 recipientMemberId, bytes32 envelopeId, bytes ciphertext)`
- `docs/specs/gas-webhook.md` selector — `send(bytes32,bytes32,bytes)` (matches contracts)

Contracts/gas-webhook order is what code generation will produce. Update master spec.

### H7. PushEnvelope `event` field type/name disagreement (sidecar vs indexer proto)
The gRPC `.proto` is supposed to be shared. The sidecar spec's copy says `EventBlob event = 1` with a custom type that's never defined; the indexer spec's copy says `bytes event_data = 1`.

- `docs/specs/sidecar.md:285` — `EventBlob event = 1;`
- `docs/specs/indexer.md:268` — `bytes event_data = 1;`

Indexer spec is correct. Update sidecar copy + remove the dangling `EventBlob` reference.

### H8. `RpcReproStub` and `IndexerAttestation` referenced but undefined in sidecar
The sidecar's proto block references both types in PushEnvelope but never defines them. The indexer spec is where the definitions live.

- `docs/specs/sidecar.md:285-287` — references both, defines neither
- `docs/specs/indexer.md:278-287` — defines both

Either drop the duplicate proto from sidecar and let it import from indexer.md's canonical version, or add the missing message definitions to the sidecar's copy.

### H9. MessageFacet `DuplicateEnvelope` revert behavior under-specified in §3.2
Master spec §3.2 describes `envelopeId` as a sender-chosen identifier "so duplicates can be detected by the reader" — i.e. reader-side dedup. But §8.2, §8.6, and §13 item 14 all assume the *contract* reverts with `DuplicateEnvelope` on a duplicate (which is how the CSK-onboarding race is dedup'd at zero protocol cost). Contracts spec §5.2 implements the contract revert.

- `docs/specs/teemesh-coordination-layer.md:128` — needs to add the on-chain dedup check.

### H10. IndexerRegistry chain-target contradiction within the master spec
§6.3 says "Base mainnet for v1"; §11 (v1 scope) and §13 item 4 say Sepolia for v1, mainnet for milestone B.

- `docs/specs/teemesh-coordination-layer.md:242` — Base mainnet for v1 (wrong)
- `docs/specs/teemesh-coordination-layer.md:432, :470` — Sepolia for v1 (correct)

Update §6.3 to say Sepolia for v1.

### H11. Missing `acceptOwnership()` in gas-webhook selector allowlist
After `deployCluster`, the cluster Safe must call `acceptOwnership` on the diamond to assume DiamondCut authority. The gas-webhook allowlist (gas-webhook.md §7) does not include this selector. If the cluster Safe is operated via 4337 (the spec explicitly anticipates this for ops Safes), it cannot complete cluster bootstrap through the webhook.

- `docs/specs/gas-webhook.md:148-167` — allowlist
- `docs/specs/contracts.md:434, :658, :735` — references `acceptOwnership` as required

Add `acceptOwnership()` to the allowlist.
