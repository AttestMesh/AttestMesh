FINDINGS
--------------------------------------------------------------------------------

CRITICAL: none. Nothing is broken; every component compiles and its tests pass.

HIGH
----
1. **Docs overclaim completeness — the sidecar bring-up is milestone-A, undisclosed.**
   `state::run()` is a v1 stub: it derives keys, discovers the cluster, sets
   `Phase::Registering`, then only starts the health server and returns.
   Registration, Indexer subscription, peer exchange, heartbeats, CSK, and the
   gRPC servers are built and unit-tested but **never wired into the run path**.
   Yet `docs/specs/sidecar.md` is headed "Implemented v1" and reads as fully
   operational; `attestmesh-coordination-layer.md §11` lists v1 as "a working
   three-node demo… converging the wireguard mesh"; and `README.md` swings the
   other way ("pre-alpha… being built fresh… component directories land as the
   matching specs get generated") despite all 4 components existing. No artifact
   honestly states: *module-complete + test-green, but the binary cannot yet
   register a node end-to-end.* (This is premortem `1780517097` finding H —
   "IMPLEMENTED + green" read as deploy-ready — surfacing in the specs.)
   → This is the "incomplete, not dead" path: keep it, but label it.

2. **No cross-language conformance test pins the `dstack_register` ABI/selector.**
   The new 8-field `DstackProof` selector `0x537d491c` is asserted ONLY in the
   TypeScript webhook test (`services/.../test/selectors.spec.ts`). It appears in
   ZERO Rust and ZERO Solidity files. The three encoders — sidecar alloy `sol!`
   (`sidecar/src/chain/abi.rs`), contracts `IDstackFacet.DstackProof`, webhook
   tuple (`selectors.ts`) — are hand-kept in sync with no test that emits the
   sidecar's actual calldata and round-trips it through Solidity. A field-order
   or type edit in any one diverges silently → on-chain revert or webhook
   mis-gate. (Also flagged in premortem `1780517097` finding G.)

MEDIUM
------
3. **`isAppAllowed` boot-gate bootstrap circularity (the known deadlock).**
   `DstackFacet.isAppAllowed` returns `(false,"appId not a cluster member")` when
   `memberIdOf[appId]==0` (`DstackFacet.sol:118`), but `memberIdOf` is written
   only by `dstack_register`, which needs a KMS proof obtainable only from an
   already-booted CVM — and the KMS calls `isAppAllowed` at boot. No pre-
   registration / admin-allowlist path seeds `appId`. Already flagged as the
   recommended follow-up in `dstack-auth-extraction.md` Open Questions §3 and in
   premortem `1780517097` (most-likely + contributor to most-dangerous failure).

4. **Master spec §4.2 overstates what the KMS chain proves.**
   `attestmesh-coordination-layer.md:193` says the chain "proves the derived key
   was granted to a CVM running an **approved compose hash on an approved
   instance**." Post-extraction the on-chain chain does NOT verify compose hash
   (dropped at registration, moved to the boot gate); it proves only that the
   node booted through a trusted KMS root. The 3-link shape and bind preimage on
   that line do match the code; the compose-hash claim does not.

5. **`README.md` is stale on build state.** Describes the repo as pre-
   implementation ("being built fresh", "component directories land as specs get
   generated") though all 4 components are implemented with 155 passing tests;
   the Test section lists only `forge test` + `cargo test` (omits the indexer and
   the webhook's 65 `npm test`).

ON "DEAD CODE" — IT IS INCOMPLETE, NOT DEAD
--------------------------------------------------------------------------------
The unwired sidecar surface (`BundlerClient` incl. the F2 fix, `AgentService` gRPC,
`dstack_facet::{assemble_proof, build_register_calldata, KmsChainMaterial}`,
`wrap_execute`/`build_send_calldata`) is **milestone-A incompleteness, not dead
code**. It is `pub`, spec'd (`sidecar.md §7/§8/§12`), and unit-tested in isolation;
it is simply not yet constructed from the stub `run()`. The blocking seam is that
the `DstackRuntime` trait (`sidecar/src/dstack.rs`) exposes only
`derive_key/get_quote/seal/unseal` — there is **no KMS-sig-chain request method**,
so `KmsChainMaterial` can't be populated from the runtime yet, and the real dstack
KMS-chain protocol can't be validated without a live node. The correct action is to
keep it and disclose its status (finding 1), not delete it. No genuine orphans were
found.
