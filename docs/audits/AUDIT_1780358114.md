## Findings fixed in this pass (commit `<this commit>`)

### F1. [MEDIUM] Wrong packed CIDR in the DeployCluster config example — *pre-existing, not a rebrand artifact*

- `contracts.md` §12.2 deploy-config example had `"meshCidrIp": 167903232` commented `// 10.13.0.0 packed`. But `167903232 = 0x0A020000 = 10.2.0.0`. The correct packed value for `10.13.0.0` is **`168624128` (`0x0A0D0000`)**, which is what the same file already uses in §4.1 and §8, and matches the master spec default `10.13.0.0/16`. A deploy script copying §12.2 verbatim would have seeded the wrong mesh subnet. **Fixed**: value corrected to `168624128` and the comment annotated with `(0x0a0d0000)`.

### F2. [LOW] Join invariant omitted the proof-validity check

- The new §1 join invariant listed only the allowlist match and the key binding, but §4.1 defines **three** registration checks (proof validity/freshness, allowlist, key binding). **Fixed**: invariant now reads "present … a **valid** proof that …", folding in the validity check.

### F3. [LOW] Enumeration-array name drift between master and contracts

- Master §3.1 described the enumeration index as `members[]`; the canonical struct field in `contracts.md` §4.1 is `bytes32[] memberIds`. **Fixed**: master now references `memberIds`.

### F4. [LOW] One missed CVM→node generalization in a §10 heading

- Master §10 bullet heading still read **"Curve25519 for the CVM's operational keys"** while the parallel §13 item 2 heading had been generalized to "the node's operational key path." **Fixed**: heading → "Curve25519 for the node's operational keys." (The bullet *body* correctly retains "per-CVM secp256k1 key" — that is genuinely dstack-specific.)
